Trade Research

A multi-agent research assistant for stocks and options. You chat with a Lead Analyst who consults a team of specialists, each with its own model, instructions and data sources. Sessions are saved, so you can come back and continue any conversation.

The main parts

SkillsReusable prompts with fields (e.g. {ticker}), a model and optionally a scanner and data sources.Skills tab
ScannersRule-based or IBKR market scans that return a results table. No AI model runs.Scanners tab
TeamThe Lead Analyst and the specialists: model, instructions, data sources.Profile menu → Team

This tool is for research and education. It is not financial advice, and it never places, changes or cancels orders.

Getting started

Requirements

  • Python 3.11+ with uv, and Node 20+.
  • At least one model: an API key for a vendor (e.g. Anthropic) or a local model server.

First run

cp -n .env.example .env        # then add your keys
cd backend && uv sync && uv run uvicorn app.main:app --reload --port 8321
cd frontend && npm install && npm run dev   # http://localhost:5173

The database is created at data/trade_research.db and filled with the default team, data sources, skills and scanners on first start. Defaults you delete are not recreated.

Restart the backend after editing .env. The --reload option only reacts to code changes, not to .env. Use cp -n (never plain cp) so an existing .env is never overwritten.

Updating

git -C ~/trade-research pull

Then restart the backend and reload the browser page. Your .env and data/ folder are never touched by updates.

How it works

You ask a question→Lead Analyst plans→consults specialists (in parallel)→specialists call data tools→Lead writes the answer
  • The Lead Analyst decides which specialists a question needs, asks them, weighs their findings and writes the answer.
  • Each specialist is an agent with its own model and data sources. It calls tools (price history, filings, news…) and reports back.
  • The app runs every tool call itself. Models only request a tool with inputs; the app fetches the data and returns it.
  • Everything is recorded: the conversation (including hidden tool calls and specialist reports) and a trace of every run with tokens and cost.

Research sessions

  • New research starts a session. Sessions are listed on the left; right-click one to rename or delete it.
  • Model picker (bottom left of the box): the Lead's model for this session. Only models that are usable are listed: vendors with an API key, and local models you added while their server runs. Local models show a loaded / not loaded badge.
  • Attach PDFs, images or text files. Documents are visible to the Lead, who passes relevant excerpts to specialists.
  • Skills button: run a skill from inside a session.
  • Timeline (left edge of the chat): a marker per turn; hover to preview, click to jump.
  • A running question keeps running if you switch sessions or pages; the session shows it is working.

Follow-up questions

The Lead keeps the whole session in context, including the specialists' earlier reports. A follow-up builds on what is already known and consults only for what is missing. Follow-ups always use the Research default model (the Lead Analyst's model, or the one you picked in the model picker) and the full team.

Run cards

Sessions started by a skill or scanner begin with a run card instead of a normal message: Skill · name (blue, dashed outline) or Scanner · name (green, solid edge). Forked sessions keep the card.

Answer actions

Under each answer: the model, time, cost and specialists consulted, plus Save as skill, Fork chat (copy the session up to that answer), copy, and thumbs up/down.

Answers, tables & suggestions

Interactive tables

  • Click a column header to sort (again to reverse). Sorting understands $1,234, +18.4%, 4.1B and (3.4%) as negative; blanks sort last.
  • Hover highlights a row; click a row (or click the table and use ↑ ↓) to select it.
  • Signed numbers show green (+) or red (−).
  • Tables with more than 5 rows get a row filter and Copy CSV (copies the visible rows in their current order). Long tables scroll with the header kept in view.

Suggested next steps

  • Every answer ends with one to three follow-up questions that build on it. Scanner results end with ready-made questions about the top tickers.
  • Click a suggestion to put it in the box, then edit or send.
  • The latest answer's first suggestion appears as grey text in the empty box: press Tab to use it, or just type your own question.

Trace & cost

Show trace (top right of a session) lists every run: the Lead's turn and each specialist it consulted, with model, time, tokens and estimated cost.

  • Expand a run to see what it was asked, the tools it called (with inputs and a preview of results) and its output.
  • Each tool call shows its result size in tokens and how much compaction saved (e.g. ≈775 tok · −68%). Large results (≈4,000 tokens or more) are amber. Claude's own web search and fetch results are marked (Anthropic).
  • Costs are estimates from the prices set on each model (Tools → Models). Local models cost $0.

Running a skill

Scan (if built on a scanner, no AI)→Skill's prompt, skill's model→Follow-ups, Research default

The run dialog asks for the fields, lets you pick a different model for this run, and shows the data notes and stages.

Save as skill

Under any answer, Save as skill drafts a skill from the conversation (prompt, fields, and the data sources the conversation used). Review and edit it before saving.

Don't add fields for things a data source fixes (e.g. a lookback window the source can't change). Put those limits in the source's notes instead.

Scanners

A scanner filters market data with set criteria and shows the matches. No AI model runs and nothing is charged. You then ask about the results.

Types

TypeHow it scansSettings
Rule-basedComputes indicators from Yahoo daily bars for each ticker in your list and applies your rules.Universe (tickers), rules, sort, max results.
IBKR market scannerIBKR scans the whole market through IB Gateway, ranked by IBKR. Results get indicator columns from Yahoo; optional rules filter them further.Scan type, market, results requested (max 50), min price, min volume, min market cap ($M), extra rules, sort.

IBKR scan types

Top % gainers · Top % losers · Most active (shares) · Most active (dollar volume) · Hot by volume (vs average) · Most trades · Near 52-week high · Near 52-week low · Widest price range · Unusual option volume · Most active options · Highest option implied volatility · Implied vs historical volatility (highest) · Biggest IV increase · Highest put/call volume ratio · Lowest put/call volume ratio.

Markets: US listed stocks (NYSE, Nasdaq, AMEX…), all US stocks (incl. OTC), Nasdaq, NYSE.

Rules

{"all": [ {"field": "close", "op": ">", "field2": "sma_200"},
          {"field": "rsi_14", "op": "<", "value": 40} ]}

Combine with all, any, not. Fields: close, volume, avg_volume_20, rel_volume, sma_20, sma_50, sma_200, rsi_14, macd, macd_signal, macd_hist, atr_14, pct_change_1d/5d/20d, high_52w, low_52w, pct_from_52w_high. Sort by a field; prefix - for descending (for IBKR, empty keeps IBKR's ranking).

What a run shows

  • The run card: scan, market, filters and the market session (open, pre-market, after hours, closed, weekend). Outside regular hours IBKR results are often few or stale.
  • The results table, a warning when IBKR returns far fewer rows than requested, and a note that indicator columns come from Yahoo's last close while IBKR ranks on live or extended-hours prices.
  • Suggested questions about the top tickers.

Run dialog changes (results, price, volume, market cap, tickers) apply to that run only.

Scanners vs. skills

A scanner finds candidates; a skill reasons about them.

ScannerSkill
PurposeSurfaces tickers matching rules or filters (price action, volume, options metrics).Packages repeatable reasoning or a research workflow for the AI team.
How it runsIBKR scanner or the rule engine. No AI model, no cost.The Lead runs the prompt with the skill's model, consulting specialists as needed.
Speed & dataFast, mechanical filtering over many stocks.Slower; better at context, synthesis and multi-step logic.
CustomizationScan types, filters and JSON rules.Natural-language prompt with fields, a model, optional data sources.
Cost & controlFree; only surfaces matches.Costs what its model costs; calls tools within the app's guardrails (read-only data, no orders).

Using them together

  • Scanner, then your questions: scan, look at the table, ask about the names you care about. You only pay for analysis you ask for.
  • Skill built on a scanner: for an evaluation you repeat, e.g. "rank today's top gainers for swing setups".
  • Skill on its own: analyses that start from a ticker or a question (full analysis, earnings preview, options strategy).

The Local models panel

  • Each server shows whether it's running. Each model shows a green dot when loaded, or "not loaded".
  • + Add to models makes a model selectable everywhere; added models show "✓ in your models".
  • Embedding models are hidden. A warning appears when a model is loaded with less than 16,384 tokens of context.

Choosing and running local models

  • Tool calling is required for the Lead to consult the team and for specialists to use data. A model without it still answers, but on its own.
  • Context length: set at least 32,768 in LM Studio's load settings, and set context overflow to stop at limit so overflow shows an error instead of silently dropping the middle of the conversation.
  • Format: on a Mac prefer MLX builds; use GGUF when no MLX build exists or tool calling misbehaves.
  • Memory (4-bit): ~5 GB for 7–8B, ~9 GB for 14B, ~15–20 GB for 24–32B, plus room for context.
  • Dense vs. mixture-of-experts (MoE): MoE models use only a few billion parameters per token, so they're several times faster for similar memory, with slightly lower quality than a dense model of the same total size.
  • Best fit: a Claude Lead with local or Haiku specialists gives most of the quality at a lower price. A large dense local Lead is slow, because the Lead re-reads every specialist report.

Adding a vendor

Put its key in .env, add a connection naming that variable, then add data sources on it. MCP servers need no code; REST APIs need a small built-in Python tool.

DuckDuckGo limitations

Unofficial (no API key or guarantees), rate-limited by IP, snippets only, variable quality. The app runs one search at a time, at least a second apart, retries rate limits twice, and treats "no results" as a normal answer. It works with any model, including local ones.

Interactive Brokers (IB Gateway)

  1. Install IB Gateway (Stable), log in (paper first), and in Configure → Settings → API enable ActiveX and Socket Clients. Keep Read-Only API on.
  2. If your port isn't 4002 (paper IB Gateway), set IBKR_PORT (4001 live; TWS 7497 paper / 7496 live).
  3. Tools → Connections → Interactive Brokers (IB Gateway) shows whether it's reachable.
  • Market data: real-time needs IBKR subscriptions; otherwise data is delayed and results say so (IBKR_MARKET_DATA_TYPE=3).
  • Option chain: one expiry per call, strikes near the money (8 each side by default, up to 20), bid/ask/last/volume, model IV and greeks, next 12 expirations. No open interest.
  • Daily logins: turn on Auto restart (Configure → Settings → Lock and Exit) and keep the computer awake.

Unavailable sources prompt

Before a question runs, the app checks the data sources of the team members involved. If some are unavailable (e.g. a missing key, IB Gateway not running), it holds the question and asks in the chat:

  • Grouped by cause, with the impact: high when a specialist has no other working source for that kind of data, low when another covers it.
  • Continue, Continue and don't ask again in this session (until the set of unavailable sources changes), or Cancel.
  • The held question and your decision are saved in the session. Sources you disabled yourself aren't reported.

How a question runs

  1. Checks: the unavailable-sources check (held for your decision if needed).
  2. Model: a one-time model for this turn if set (a skill's run), otherwise the session's model, otherwise the Lead Analyst's model. A chosen model without a key or server falls back to the Lead Analyst's model.
  3. Scope: a skill that names data sources limits its own run to them; specialists left without sources aren't offered to the Lead. Follow-ups use the full team.
  4. Lead loop: the Lead reads the whole session, then consults specialists (in parallel when it asks for several at once) within the team limits.
  5. Specialist loops: each specialist calls its data tools; results are compacted and paged (details); it returns a report.
  6. Answer: the Lead writes the answer, ending with suggested next steps. Everything is saved and traced.
  7. Queued stages: some runs chain stages in one background task; they continue even if you leave the page, and stop if a stage fails.

Scanner run

The scan runs (no AI); the session gets the run card and results; nothing else runs until you ask.

Skill built on a scanner

The scan runs (no AI); then the skill's prompt runs on the results with the skill's model; it's told to work only with the scanned tickers and to flag odd results (few rows, market closed) instead of substituting its own list.

Team limits

The Lead is told to ask each specialist once per question with every ticker in one consultation, to make all consultations in the same step, and to re-consult only to fill a specific gap.

Default (every Lead)Strict team mode (opt-in, per model)
Consultations per specialist, per question21
Consultations in total, per question53
Specialist reportsas writtenabout 250 words; over 6,000 characters trimmed

Requests over the limits aren't run; the Lead is told to answer with what it has.

Tool results & compaction

Each step of an agent re-sends the whole conversation so far, so a large tool result is paid for again at every later step. Results are kept small without losing information:

  • Compaction (lossless): JSON lists of similar objects become tables (columns + rows, field names once); empty fields dropped; floats rounded to 4 decimals (4 significant digits below 1); no whitespace. Applied only when smaller.
  • Paging instead of cutting: results over 16,000 characters (~4,000 tokens) are sent as a first page ending at a line break, with a note on what's left. The agent reads on, or searches the whole result for a keyword, with the read_more tool.
  • SEC filings: start with a list of the filing's sections; jump with find, continue with offset.
  • Measured: the trace shows each result's size and the saving. Claude's web search/fetch results are measured but processed by Anthropic, so they can't be paged.

Full details: docs/tool-results.md in the project.

Test mode (no cost)

Turn on Test mode in the profile menu (or under Profile & settings): every team member gives canned answers instead of calling an AI model, so nothing is charged. It takes effect immediately, with no restart, and is remembered.

  • The Lead consults the most relevant specialists, specialists really call a data tool, and answers (marked "Test mode response") stream and appear in the trace, footer and timeline with $0 cost.
  • A TEST MODE badge shows in the header while it's on.
  • To test just one session's Lead, pick Test mode (no cost) in the model picker instead.
  • MOCK_LLM=1 in .env also turns it on; the toggle then shows it as set in .env and can't turn it off.

Logs

  • data/logs/backend_<date>_<time>.log: everything the backend logs, with full tracebacks and every error shown in a chat.
  • data/logs/frontend_<date>_<time>.log: browser errors (uncaught errors, failed API calls, errors during a turn).
  • A new file starts at every app start, at 5 MB, and at midnight. Files older than 14 days are deleted, and the oldest go once a kind passes 200 MB.
  • backend-latest.log / frontend-latest.log always point at the current files.
tail -F ~/trade-research/data/logs/backend-latest.log ~/trade-research/data/logs/frontend-latest.log

Safety & privacy

  • No trading: any tool that places, changes or cancels orders, or moves money, is never exposed to the agents. Brokerage access is read-only.
  • Secrets stay in .env; the database only stores the variable names. Keys are never returned by the API.
  • Local models keep your conversation on your machine; data requests still go to the data providers.
  • Research only: answers are research and education, not personal financial advice.
